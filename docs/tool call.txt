Q:如果deepseek model 需要绑定duck search tool，为啥一个user query，
会带来model返回两个search query呢？两个search query我需要调用两次duck search tool对吗？然后怎么聚合结果？
Answer：
一个用户查询引发两个搜索请求，这并非偶然，
而是 DeepSeek 为高效处理复杂查询所采取的主动策略。
它的核心逻辑是：将你的原始复杂问题拆解成多个独立的子任务，
以并行调用的方式（Parallel Tool Calls）一次性地全部推送给开发者.
处理结果就可以多个messages list一起发给model做总结。


要理解具体怎么执行，还得先从 DeepSeek 工具调用的工作流程说起。

### 🚀 工作流程：意图识别与手动调度

这里首先要明确一点：DeepSeek 模型只负责识别意图并输出结构化的调用请求，它本身不执行任何函数。真正的执行、数据获取，都是开发者需要在自己的代码里完成的。整个过程在 Agentic Loop 循环中进行，一般包括以下四步：

1. **用户提问 & 模型响应**：用户在对话中输入一个问题。
2. **模型识别与返回**：模型判断需要调用工具，并在响应中返回一个或多个结构化的 `tool_calls` 指令。
3. **开发者执行**：你（开发者）解析 `tool_calls` 指令，去执行真正的函数调用，比如去调用 DuckDuckGo 搜索 API。
4. **结果回传**：你将获取到的函数执行结果，通过特定格式的 `tool` 角色消息再反馈给模型。

### 📝 问题拆解：模型为何会返回两个搜索请求？

这是模型**并行工具调用（Parallel Tool Calls）**能力的体现。当 DeepSeek 认为你的单一查询可以通过并行分解来提升效率和信息完整性时，就会在单次响应中返回一个包含两个 `tool_calls` 的数组，每个 `tool_call` 都是一个独立的搜索请求。

例如，当用户提问“比较一下 iPhone 15 和三星 S24 的相机性能”时，模型可能会如此响应：
*   **search_call_1**: 搜索 “iPhone 15 相机性能 评测”
*   **search_call_2**: 搜索 “三星 S24 相机性能 评测”

### 🛠️ 如何处理并行工具调用？

当模型返回两个 `tool_calls` 时，你的代码可以通过以下步骤完成整个调用流程：

1. **解析调用列表**：从 API 的响应中提取 `response.choices[0].message.tool_calls` 数组。每个元素都包含调用的唯一 `id`、工具名 `function.name` 和参数 `function.arguments`。
2. **并行/顺序执行**：你可以在代码中，并行或顺序地调用两次 DuckDuckGo 搜索 API。并行执行能显著缩短总响应时间，这也是模型采用此策略的初衷。
3. **格式化并回传结果**：获取两次搜索的结果后，将它们按顺序添加到 `messages` 数组中。每个结果都要对应唯一的 `tool_call_id`。

```python
# 假设 tool_calls 数组中有两个任务
for tool_call in tool_calls:
    if tool_call.function.name == "duckduckgo_search":
        # 解析参数
        query = json.loads(tool_call.function.arguments)["query"]
        # 执行搜索
        result = duckduckgo_search(query)
        # 准备回传结果
        messages.append({
            "role": "tool",
            "tool_call_id": tool_call.id,
            "content": json.dumps(result) # 将结果转为字符串
        })
```

### 🤝 聚合结果：AI如何理解并总结信息

将搜索结果回传给模型后，模型会读取所有 `tool` 角色的消息，以理解所有结果。然后，它会像处理普通对话一样，生成一个整合了所有信息的、最终的总结性回答。这通常无需特殊的“聚合”代码，只需将包含所有工具调用结果的 `messages` 数组再次发送给模型即可。

### ⚠️ 空结果的根源：被破坏的推理链条

这是你在工具调用流程中最可能踩的坑，尤其是在使用 DeepSeek-V4 等具备“思考模式”（Reasoning Mode/Thinking Mode）的模型时。

*   **根本原因**：在思考模式下，模型的部分推理过程（`reasoning_content` 字段）被视为对话状态的一部分。尤其是在进行多轮工具调用时，如果后续 API 请求中**没有完整回传**这些 `reasoning_content`，模型就会因为无法衔接上下文而拒绝生成内容，返回空结果。

*   **解决方案**：
    *   **使用普通模型**：使用 `deepseek-chat` 这类非 V4 的普通模型进行开发。
    *   **确保完整性**：务必在每次工具调用的后续请求中，完整地回传从之前 API 响应中接收到的所有必要信息，尤其是 `reasoning_content`。

### 🧠 核心差异：工具调用 vs. 非工具调用模式

这两种模式的区别在于**模型的“思维方式”和工作内容**。
*   **非工具调用模式**：模型只会输出一个最终的自然语言回答。
*   **工具调用模式**：模型思考“何时需要调用工具”，输出的是`tool_calls`请求。整个过程变得更加结构化，包含意图识别、参数生成、结果整合等多个步骤。`deepseek-chat` 及部分旧版模型原本默认启用此模式，而许多新版思考模型则需要 `tool_choice` 参数明确指定后才能强制启用。

除了模型本身的处理逻辑不同，工具调用下的特殊参数可能导致空结果。通过设置 `tool_choice` 参数，可以显著影响模型的行为：
*   **`tool_choice: "auto"` (默认)**：模型自主判断，可能会因函数描述不清晰等原因而不触发工具调用。
*   **`tool_choice: "none"`**：模型完全不会调用工具，只输出纯文本。
*   **`tool_choice: {"type": "function", "function": {"name": "my_tool"}}`**：如果你在开发中明确并强制模型调用特定工具，`none` 的优先级最高，会覆盖其他设置，导致模型直接输出文本而不触发任何调用。
